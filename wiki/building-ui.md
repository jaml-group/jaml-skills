# Building a JAML UI

Use this shared path for a dashboard, landing page, form or application. Combine the scenario choices below when a product contains several of them. For language syntax, start with the [tutorial](tutorial.md); API details remain in their linked owner pages. A design or dry run produces a plan; it does not authorize implementation.

## Shared design-to-verification path

1. **Define the experience and host.** Record the user operations, data sources, empty/loading/error states, accessibility, responsive behavior and success criteria. Identify the installed runtime and the host: a standalone page, an embedded region or a desktop/web application. Use the [standalone app-root convention](JAML/component.md#standalone-application-root) only for a full-page shell; embedded content keeps its [intentional host boundary](JAML/component.md#embedded-application-hosts). A landing page normally uses document flow; a dashboard may need a constrained work area. Choose scrolling and geometry from the experience, not from a copied desktop scaffold.
2. **Choose capability owners.** Follow [intent-first selection](#choose-elements-by-user-intent): establish the behavioral contract before choosing a [native element](JAM-UI/JAM-UI.md), [public style](Styles/styles.md) or [plugin](Plugins/plugins.md#choose-an-entry-point). For controls, feedback, layout, scrolling, charts or shared behavior, follow [Choose native capabilities](choosing-native-capabilities.md). Read the selected detail page, inheritance and limitations. Record any gap and the reason for a custom implementation. Assign [roles](Theme/stylize.md#common-choices) to meaningful regions, then choose [layout styles](Styles/common/layout.md) for their geometry. Roles alone do not promise a complete layout; layout builders require verified target-runtime support.
3. **Separate appearance and composition.** Apply the [style ownership decision](Styles/styles.md#style-ownership-and-composition) before creating CSS. Reuse the existing theme's visual language and generic state recipes; keep local geometry with its component, and share actual repeated composition through the smallest suitable [CC, builder or usage](JAML/component.md). Register a shared style for repeated presentation without inventing a new component. Ordinary feedback uses native [success/warn/error semantics](color.md#semantic-colors). A new theme, token family or domain palette requires an actual missing contract, not merely a new screen.
4. **Assign data, state and lifecycle.** Define each value's owner, initial state, update path and teardown. Use [bindings](JAML/binder.md) and [JAML controls](JAML/jaml-format.md) instead of a second reactive system; inspect native localization for text that needs translation. Keep external records in runtime model data, separate from trusted definitions. Decide route/draft/selection persistence, asynchronous stale-result handling and editor or platform adapters explicitly. Check native cleanup contracts before adding listeners or observers.
5. **Build one complete slice, then reuse.** Connect an actual operation to its data, controls, feedback and failure path. Co-locate its presentation, and register extensions after runtime readiness but before their consumers render. Extract recurring structure when its inputs, behavior and lifecycle are clear. Keep valuable app-specific behavior behind a bounded adapter when native capabilities do not satisfy its contract. Do not create empty extension directories or abstractions solely to match a scaffold.
6. **Verify the chosen contracts.** Run syntax/registry checks, then authorized runtime checks for visible geometry, keyboard/focus, state changes, layout/scrolling, cleanup and relevant modes/breakpoints. Test the meaningful empty/loading/failure/retry cases. Report static and live evidence separately. For refactors, compare against the preservation baseline and reconcile every proposed style owner with the actual files. Identify reusable extension or framework candidates with evidence and approval status; implementation or promotion needs its own authorization.

Before implementation, the design should name capability owners, structural roles, layout/scroll boundaries, theme versus local style ownership, state/lifecycle boundaries, extension locations and verification cases. Reuse existing project conventions; Jam-UI framework maintenance follows its own source architecture rather than application scaffolding.

## JAML composition principles

Ask: **Who owns this state, who publishes it, and who consumes it?** Use the native semantic owner when one exists. Prefer published state and listening consumers for shared application state; direct events and cross-component control remain supported when simpler or more appropriate. A renderer may fetch its own runtime data. For one dataset shared by several consumers, prefer a dedicated `data` owner; conditional request sharing is an efficiency mechanism, not a substitute for ownership. Avoid unnecessary orchestration and rebuilding native behavior from generic containers.

See [state and data composition](JAML/state-and-data.md) for actionable examples and request limits. These are preferred patterns, not restrictions on valid JAML.

## Choose elements by user intent

Use this order: **user intent → behavioral contract → native owner → theme/local presentation**. Identify what the user accomplishes, what state changes, and which controls jointly own that operation. Establish selection cardinality, activation, keyboard/focus, navigation or panel relationships, disabled behavior and lifecycle before choosing an element. Then compare the relevant native element and public styles/plugins with that contract.

During a refactor, infer intent from handlers, bound state, visibility changes and navigation—not only existing tags, class names or visual resemblance. A container of buttons can implement a coordinated selector; moving its CSS beside the container does not establish that the abstraction fits. Record the native alternative, the contract it covers, any verified gap and the preservation checks for a custom solution.

A coordinated set of buttons serving one purpose warrants a [buttongroup](JAM-UI/button-group.md) assessment, whether the operation is exclusive or not. Selection of one value, independent toggles and related commands have different contracts. Verify that the installed group supports the required mode; retain a justified composition or propose a bounded extension when it does not. Mere adjacency does not establish a shared operation.

| User intent                        | Native candidate and distinction to establish                                                                                                                                                                                                                                                                                                               |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Choose one value                   | Compare native single-selection controls, including `buttongroup-radio`, radio options or select, against the input and keyboard contract. Button-shaped presentation alone does not choose the interaction pattern.                                                                                                                                        |
| Toggle several independent values  | Compare multi-selection `buttongroup-checkbox`, checkbox options or individual switches. Preserve independent state and any select-all policy.                                                                                                                                                                                                              |
| Invoke related commands            | Evaluate `buttongroup` support for the command contract and compare a composition of native buttons. Do not introduce persistent selection merely to obtain a grouped appearance. A toolbar has its own focus/keyboard contract.                                                                                                                            |
| Switch one visible content section | Evaluate native grouped selection plus the content host's activation, visibility and lifetime contract. Start with plain `buttongroup-radio`, whose checked state is already visible, and let content consume its published selection. Add [`check.underscore`](Styles/check.md#checkunderscore) only for an optional underline; it does not manage panels. |
| Navigate to a destination          | Preserve link/route behavior and browser navigation expectations. A selected appearance alone does not make links a radio group or tabs.                                                                                                                                                                                                                    |

Keep grouping distinct from an accessible tabs, radio-group or toolbar pattern. A complete tabs composition must own selection-to-panel relationships, focus/activation policy and panel lifecycle; `buttongroup` plus an underline does not by itself establish those guarantees. Verify the intended pattern and its implementation rather than adding ARIA roles as decoration. The [W3C Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) defines tabs behavior, while [ARIA's role promise](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/#a-role-is-a-promise) explains why a role alone does not implement it.

Finish the choice with a concrete native owner or an evidenced gap, then apply the theme and component-local styles. Capability selection remains part of design, build, refactor and validation; syntax validity or tokenized CSS does not prove the interaction owner is correct.

## A small composable slice

This embedded tile demonstrates roles, local geometry, reactive state and semantic feedback. It counts local button presses; it does not implement persistence or a remote save. In a dashboard, compose the tile under the work area's `main`; do not wrap every reusable tile in an `app` root.

```javascript jaml-playground
export default {
    type: 'card',
    stylize: 'tile',
    vars: { count: 0 },
    components: [
        {
            type: 'container',
            stylize: 'section',
            styles: ['css(display:flex;flex-direction:column;gap:s)'],
            components: [
                { type: 'label', stylize: 'title', cap: 'Local activity' },
                { type: 'indicator', cap: 'Recorded presses', value: '{{count}}' },
                { type: 'label', cap: '{{count > 0 ? "Recorded" : "Ready"}}', color: '{{count > 0 ? "success" : "info"}}' },
                { type: 'button', cap: 'Record a press', onclick: 'this.model.vars.count++' }
            ]
        }
    ]
};
```

If this structure recurs, evaluate a builder or CC with an explicit input/state contract; a shared stylesheet cannot provide that contract. If only the visual treatment recurs, reuse a public style or shared recipe instead. The [component API](JAML/component.md) distinguishes the available extension forms and their ownership.
