# Validate

Use `validate_jaml` as the static baseline when available. Omit `fileName` for unknown playground formats; use an explicit JAML extension only when the input format is known.

Inspect:

-   Element types, inheritance, parameters, control keys, argument forms and render contracts.
-   [Composition review pass](../references/JAML/purpose-and-composition.md#review-the-reasoning-as-well-as-the-syntax): compare the implementation with the design's complete operation candidates, selected owners, parts and remaining custom work; trace shared helpers to the definitions they return; check both duplicated native parts and [overloaded hosts](../references/JAML/purpose-and-composition.md#choose-the-owner-before-the-slot). Captions, icons, values and units reuse their native owner; slot additions fit that owner's responsibility; containers express a real relationship; CCs expose caller-independent contracts. A shared record or a domain noun in a caption does not establish ownership. Assess responsibilities rather than enforcing a wrapper count. Exercise independent instances or additional consumers when reuse is claimed.
-   [Interaction and presentation fit](../references/JAML/purpose-and-composition.md#choose-interaction-and-presentation): inspect the actual path from trigger through completion and return, including visual/pointer travel, repeated prompts, unnecessary blocking, anchor visibility, keyboard access and narrow viewports. Verify pending, failure/retry, cancel and owner replacement. A correct native API can still present the wrong interaction; compare Rename with its nearby-edit example.
-   [Helper construction and lifetime](../references/utils.md#dialog-and-popup-ownership): distinguish definition, Model and built element; verify callback receiver, return value, dismissal timing and settlement guarantees. Exercise [asynchronous transitions](../references/JAML/purpose-and-composition.md#own-asynchronous-operations): duplicate activation, failure then retry, departure before settlement, replacement on the same anchor and concurrent backend changes. For Undo, verify eligibility begins after acknowledgement and ends at the actual deadline.
-   [Final builder overrides](../references/JAML/component.md#final-jaml-overrides): correct argument position and customization target, generated children retained before additions, and existing initialization/cleanup still running alongside caller hooks. Check that post-build spread or mutation has not bypassed composition, and exercise placement when adding children or slots.
-   Bindings, instance state, updates, localization, lifecycle and event ownership.
-   Custom-property plumbing: prefer [automatic `props` bridges](../references/JAML/jaml-format.md#props) over build hooks that only attach data/descriptors; check member collisions, post-`onafterbuild` timing, and the distinction between fresh reads and reactive notifications.
-   [Intent-first capability selection](../references/building-ui.md#choose-elements-by-user-intent): infer the actual operation and coordinated controls, compare native owners and verify any claimed gap. Check the promised selection, keyboard/focus and navigation/panel contract; visual grouping, syntax or an ARIA role alone is insufficient. Retain justified adapters and reusable extensions.
-   Application role/token consumption and business-color handling; [style ownership and composition](../references/Styles/styles.md#style-ownership-and-composition), including actual declaration placement, theme versus app ownership, native semantic status colors, shared recipes, reusable composition, justified adapters/pixel contracts and state/breakpoint cascade. For refactors, reconcile the reported inventory with the files and parity evidence; tokenized global selectors alone do not prove ownership was corrected.
-   Theme definitions only when that domain is part of the task.

For an interaction plugin or presentation variant, exercise the promised user sequence. A hover-action example needs target entry, popup reveal, action invocation and dismissal; check where actions appear in each requested variant and retain deliberate keyboard/touch access. Plugin presence or a directly called callback proves neither the interaction nor the intended placement.

When delivering a demo, use representative content and verify that visible action names match their effects. Keep adversarial strings and assertion-only actions in clearly identified regression scenarios. A test fixture can supply evidence without being the product demonstration.

For forms, inspect the actual native input/select/textarea and exercise keyboard and pointer behavior. Host `disabled` or ARIA attributes alone do not prove that the backing control is disabled or named. Use canonical rule keys `minLength` and `maxLength`; separately test typed-input constraints and programmatically assigned values. Inspect screenshots at the intended viewport and theme: DOM overflow checks can miss clipped canvas text.

For every diagnostic, distinguish a real error from a demonstrated analyzer limitation using the owning source or runtime. A static pass cannot establish accessibility, geometry, lifecycle correctness or suitability of the chosen abstractions.

Report findings with severity, location, evidence and a concrete correction. Static analysis/review can run without a browser. For authorized live work, follow [runtime operations](runtime.md) and exercise the actual scenario, including relevant state preservation and theme changes.

Done: real issues and evidence-backed exceptions are accounted for; capability-selection and theme-convention concerns are reviewed alongside syntax. A validation-only request reports findings without editing.
